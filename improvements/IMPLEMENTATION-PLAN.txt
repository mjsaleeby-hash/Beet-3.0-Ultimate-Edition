1.1  FIX: FAT/exFAT incremental backups re-copy everything every run
     FILE: Services/TransferService.cs
     WHY:  FAT32 stores file times at 2-second resolution and exFAT at 10 ms.
           After we copy a file we stamp the destination's modified-time to equal
           the source's. The destination filesystem silently rounds that stamp
           down. On the next run the (full-resolution) source time is strictly
           greater than the (rounded) destination time, so the unchanged file is
           judged "changed" and copied AGAIN — forever. This is silent (it reports
           success) and hits the most common backup target (USB sticks / SD cards).
────────────────────────────────────────────────────────────────────────────
STEP A — add ONE shared decision helper near the other private helpers in
TransferService. This becomes the SINGLE source of truth for "did this file
change?", used by both the Copy planner and the Move path, so they can never
drift apart again.

    // ----------------------------------------------------------------------
    // Incremental-backup "has this file changed?" decision.
    //
    // BACKGROUND FOR FUTURE MAINTAINERS:
    //   Different filesystems store a file's last-write time with different
    //   precision:
    //       NTFS  -> 100 nanoseconds (effectively exact)
    //       exFAT -> 10 milliseconds
    //       FAT32 -> 2 seconds (and only even-numbered seconds!)
    //   When we copy a file we set the destination's last-write time equal to the
    //   source's. On a FAT/exFAT destination the filesystem ROUNDS that value down
    //   to its own precision. So the destination's stored time ends up SLIGHTLY
    //   EARLIER than the source's. If we then compared the two times with a plain
    //   ">", the source would always look "newer" and we would re-copy a file that
    //   never actually changed — on every single backup run.
    //
    //   The fix is to allow a small tolerance (a "close enough" window). 2 seconds
    //   covers FAT32's coarse 2-second granularity, and therefore exFAT's finer
    //   10 ms granularity as well. Windows' own robocopy tool does the exact same
    //   thing with its "/FFT" (FAT File Times) option.
    // ----------------------------------------------------------------------

    /// <summary>
    /// Maximum last-write-time difference (source minus destination) that we still
    /// treat as "unchanged". Sized to FAT32's 2-second timestamp granularity so a
    /// freshly-copied file on a FAT/exFAT drive is not re-copied forever just
    /// because the destination filesystem rounded the timestamp we wrote.
    /// </summary>
    private static readonly TimeSpan TimestampGranularityTolerance = TimeSpan.FromSeconds(2);

    /// <summary>
    /// Returns true when the destination copy of a file is out of date relative to
    /// the source, for SkipExisting / Mirror modes. A file counts as changed when:
    ///   (a) the byte length differs, OR
    ///   (b) the source was modified MORE than <see cref="TimestampGranularityTolerance"/>
    ///       after the destination.
    /// A destination that is NEWER than the source is treated as unchanged (we only
    /// ever re-copy when the source is genuinely newer) — this preserves the
    /// original behaviour. This is a length+modified-time heuristic; for byte-exact
    /// guarantees the user enables VerifyChecksums, which is a separate, unaffected
    /// step that runs AFTER the copy.
    /// </summary>
    internal static bool IsDestinationStale(FileInfo source, FileInfo dest)
    {
        // A size change is an unambiguous "changed" signal — no tolerance needed.
        if (source.Length != dest.Length)
            return true;

        // (source - dest) is positive only when the source is newer. If the
        // destination is newer or equal, the difference is zero or negative, which
        // is never greater than the tolerance, so we correctly return "not stale".
        return source.LastWriteTimeUtc - dest.LastWriteTimeUtc > TimestampGranularityTolerance;
    }
